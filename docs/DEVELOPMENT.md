# LiveGreen development notes

Everything worth knowing to keep building LiveGreen: how it is put together, which services it talks to and
why, what was measured, and the traps already found. The original product spec is
[superpowers/specs/2026-10-16-livegreen-design.md](superpowers/specs/2026-10-16-livegreen-design.md); this
file records what was actually built and changed since. No API keys belong in this file or anywhere in git.

## 1. What the app is

A sustainability scanner for iPhone (iOS 26, SwiftUI, Liquid Glass), built for HackHarvard 2026. You
photograph an item, meal or setup. The app:

1. finds the components in the photo (AI vision),
2. puts numbers on each one across 12 metrics, preferring real records over estimates,
3. asks a usage question only when the answer changes the numbers a lot,
4. suggests greener swaps and compares them like-for-like,
5. generates a picture of the greener setup in the same room (Grok image edit),
6. ranks you on a leaderboard of friends, and
7. optionally drives a Shelly smart plug so chargers run in the cleanest grid hours.

Metrics: carbon (kg CO2e), water (L), land (m²·yr), power on (W), standby power (W), yearly electricity
(kWh/yr), lifespan (yr), repairability (0–10), plastic (g, item + packaging), recyclable (%), decomposition
time (yr), water pollution (g PO₄e). Categories: food, electronic, clothing, packaging, household, personal
care. `Category.applicableMetrics` decides which metrics apply (electronics have no land or water).

## 2. Setup

```bash
brew install xcodegen
cp Secrets.example.xcconfig Secrets.xcconfig   # untracked; fill in keys
xcodegen generate                               # LiveGreen.xcodeproj is generated, not committed
open LiveGreen.xcodeproj
```

- Run `xcodegen generate` after pulling and **after adding any new Swift file**: `project.yml` globs the
  source folders, but the generated project only picks up new files when regenerated. A "cannot find X in
  scope" build error for a type that clearly exists usually means this.
- `Config/LiveGreen.xcconfig` declares every key empty, then `#include? "../Secrets.xcconfig"`, so a fresh
  clone builds without secrets. Keys reach the app through Info.plist (`project.yml` maps them) and can be
  overridden at runtime in Settings → API keys (stored in the Keychain). `Secrets.value(for:)` prefers the
  Keychain.
- `Config/Info.plist` is generated by XcodeGen and gitignored.

| Key | Used for | Needed |
|---|---|---|
| `ANTHROPIC_API_KEY` | Claude: identify, swaps, spec research (Sonnet 5.5 by default) | yes, except demo mode |
| `ANTHROPIC_WORKSPACE_ID` | `anthropic-workspace-id` header, only for a key not scoped to a workspace | only for unscoped keys |
| `XAI_API_KEY` | Grok: the greener image | yes, except demo mode |
| `ELECTRICITYMAPS_API_KEY` | Optional live grid data; without it EIA is used (no key) | no |
| `ENERGYSTAR_APP_TOKEN` | Higher ENERGY STAR rate limits | no |

The xAI key must be an **inference** API key (console.x.ai → API Keys), not a management key. Billing for
the xAI API moved from console.x.ai to grok.com in late 2026; the console Billing page no longer has a
promo-code field, and promotional credits arrive as "credit grants" applied by xAI.

Demo mode (Settings, or launch argument `-DemoMode YES`) replays three bundled scenes (desk setup, lunch,
e-bike corner) with no network calls and no keys.

## 4. Build settings and Swift gotchas

- Swift 6, `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and approachable concurrency for the **app**: every
  app type is MainActor unless marked `nonisolated`. Pure value types used off the main actor are marked
  `nonisolated` (`FeatureFlags`, `ServiceContainer`, `Secrets`, `UnitSystem`…). `DisplayUnits` is
  deliberately MainActor because it calls `Measured.format`, which is MainActor in the app.
- GreenCore has no default isolation; its types are `Sendable`.
- The UI test target is `nonisolated`.
- SourceKit in the editor shows "No such module 'GreenCore'" and similar errors in files you just edited.
  They are indexing noise; trust `xcodebuild` / `swift build`.
- When `FeatureFlags` or `UserProfile` gain a stored property, keep the custom `init(from:)` that uses
  `decodeIfPresent`, so data saved by older builds still loads instead of resetting to defaults.

## 5. Scan pipeline

`ScanCoordinator` (app) → `ScanPipeline` (GreenCore), emitting `PipelineEvent`s the analyzing card shows:

1. **Reading labels**: on-device Vision OCR and barcodes → `OCRHints` (GTINs, model-number tokens,
   wattages, fiber %, resin codes). Images are normalized first (`CapturedImage` via `IdentifyImage`:
   orientation baked in, long edge ≤ 2576 px and ≤ 3.7 MP, the Sonnet/Opus 5.5 vision limit, JPEG), so boxes
   map straight onto the displayed photo and logos and key legends stay legible. The scan keeps a copy scaled
   to 1568 px (`ScanPhoto.stored`) for History, the results screen and the Grok image edit.
2. **Identifying**: the AI provider's `identify` returns components with category, normalized box,
   identifiers, quantities, default usage, deferrable load, one fallback carbon estimate and optional
   questions. The call streams, and `.identifyProgress` events carry item names as they appear.
3. **Evidence ladder** per component and metric, first source that answers wins, tier recorded:
   - T1 exact record: Open Food Facts (GTIN), ENERGY STAR (brand + model), bundled ASUS PCF figures
   - T2 researched spec: AI web search; a value is kept only if it cites a page the search returned
   - T3 factor model: bundled tables × quantities
   - T4 estimate: the AI's fallback, widened to at least ±50%
   Results are cached by GTIN or `brand|model`, so a rescan gives identical numbers. Unbranded clothing,
   household, packaging and personal-care items are cached by their generic kind (`Identifiers.genericKey`:
   the name without colour words, singular, so "Blue backpack" and "Beige backpack" are both `backpack`), and
   items of one kind in a scan share the best-informed one's guesses. A kind's cached T4 estimate is only used
   when the new item cannot do better itself. Identify reports a brand from a legible logo or from
   unmistakable design cues (a Mac keyboard's ⌘ keys, ROG styling, an iPhone camera layout), a `model_line`
   ("MacBook Pro 14", "Zenbook 14"), the `appearance_cues` it used and a `confidence`. `model` stays a printed
   model number: an unread one moves to the model line with its brand prefix stripped and confidence capped at
   medium (low without cues), and an unread single code like "M2" stays a model only at high confidence when
   the item's own label text contains it. A medium- or high-confidence line drives spec research and the ASUS
   line records (T2 ranges); a missing confidence counts as low. Line results are cached under
   `Component.resolutionKey` = `bl:<category>|<brand>|<line>|<size>` (screen inches or mass), never for food or
   packaging, and not at all when the size is unknown, so a 43" and a 65" TV of one line never share numbers.
4. **Computing**: `ImpactEngine` derives yearly electricity, use-phase carbon from the local grid, yearly
   totals, lifecycle stage splits, with a seeded 2,000-sample Monte Carlo for ranges.
5. **Questions**: shown only if the AI asked and the metric's range is wide (high/low > 1.6) and it is a
   top-two carbon contributor (`QuestionGate`). Answers re-run the engine locally.
6. **Quick details** (before the results): items whose carbon is still T4 get at most one plain multiple-choice
   question each, three per scan, one per kind (`SpecQuestionCatalog`, generated locally). Only answers that
   really move the item to the factor model are offered; `ScanPipeline.refining` applies them. Skip keeps the
   estimates.
7. **Swaps** are prefetched in the background as soon as a scan is saved (`SwapPrefetcher`), along with the
   greener image for scenes with more than two items, so the swaps screen opens instantly.
8. **Feedback**: the results screen has an optional note field ("the TV was actually a monitor"). Notes are
   stored in SwiftData (`StoredFeedback`, `FeedbackStore`) with the scan's id, item names and categories, and
   managed in Settings → Scan feedback ("Erase all data" clears them too). Each identify call gets up to five relevant notes
   (`ScanFeedback.relevant`: shared words with the OCR text or a hinted category first, then newest) as a
   separate "Recent user corrections (hints only)" block, at most 600 characters, which tells the model to
   apply a correction only when the photo agrees and never to relabel every similar item. Claude and Grok both
   send it.

## 6. AI providers and models (measured)

Claude runs identify, swaps and research; Settings → Claude model picks Sonnet 5.5 (default, fast) or Opus 5.5.
The greener image always uses Grok. The Grok analysis client is still in GreenCore and can be selected with the
developer launch argument `-AIProvider grok`; there is no Settings switch for it. Saved flags from builds where
Grok/Opus were the defaults are ignored (the coding keys were renamed). `ServiceContainer.analysisClient` builds
the client.

### Grok (xAI Responses API, `POST https://api.x.ai/v1/responses`)

- Request: `store: false` (images can fail when stored), `instructions`, `input` with `input_image`
  (`data:image/jpeg;base64,…`, `detail: high`) and `input_text`, and strict structured output
  `text.format = {type: json_schema, name, strict: true, schema}`. The Claude prompts and tool schemas are
  reused; `GrokAnalysisClient.structuredOutputNote` tells Grok that "call the tool" means "reply with JSON".
- Research adds `tools: [{type: "web_search"}]`. Citation URLs come from `web_search_call.action.sources[]`
  and message `annotations[]` (`url_citation`). xAI returns no page text, so quotes cannot be verified
  verbatim the way Claude's `web_fetch` results allow.
- Streaming: `stream: true` gives server-sent events. `response.output_text.delta` carries text deltas;
  `response.completed` carries the full response object (`event.response`). `HTTPStreamingTransport`
  (`URLSessionTransport.lines(for:)`) reads lines; `GrokAnalysisClient.stream` parses them.
- Costs are reported in `usage.cost_in_usd_ticks` (1 tick = 1e-10 USD). Identify ≈ $0.01–0.03.

Model choices (desk photo, measured Oct 2026):

| Model / setup | Identify time | Notes |
|---|---|---|
| `grok-4.7` | did not finish in 240 s | unusable for identify |
| `grok-4.3`, full schema | 14–25 s | careful, no invented model numbers |
| `grok-4.3` + `reasoning.effort: low` | 24 s | slower, not faster |
| `grok-4.3`, `detail: low` | 16 s | worse boxes |
| `grok-4.20-0309-non-reasoning`, full schema | 15 s | copied "S2721H" from the schema example |
| **non-reasoning + slim schema** (one carbon fallback) | **8–11 s; ~12 s streamed, first item ~2 s** | **current identify setup** |

Latency is driven by output tokens, not by image detail or reasoning effort. The slim schema
(`ReportComponentsTool.carbonEstimateOnlySchema` + `identifySystemPrompt(carbonEstimateOnly: true)`) cut
output roughly in half. Defaults: `identifyModel = grok-4.20-0309-non-reasoning`, `model = grok-4.3` for
swaps and research. Never put a concrete example identifier in a schema description; the fast model copies
it into answers.

Bounding boxes from Grok are rough (average IoU ≈ 0.33 against hand-measured boxes, in every coordinate
format tried: fractions, 0–1000 grid, pixels). Center points land on large items but miss small ones. The
results screen therefore shows numbered pins at box centers rather than outlines. Apple's
`VNGenerateForegroundInstanceMaskRequest` merged the whole desk into one instance, so it cannot separate
items. A bundled detector (Apple's YOLOv3-Tiny Core ML, 8.9 MB) was considered and not added.

### Grok image edit

`POST https://api.x.ai/v1/images/edits`, model `grok-imagine-image-2.0`, body
`{model, prompt, image: {url: "data:image/jpeg;base64,…", type: "image_url"}}`; the response has
`data[0].url` or `b64_json` (both handled). About 10 s per edit; it keeps the scene and changes only what the
prompt names. Output is 1024×1024.

### Claude (Anthropic Messages API)

`claude-sonnet-5-5` (default) or `claude-opus-5-5`. These models reject `temperature` and a forced
`tool_choice` with a 400, so `ClaudeToolLoop` uses `tool_choice: auto`, checks the call happened, nudges
once and sends decode errors back as `is_error` tool results. Research uses the `web_search` and
`web_fetch` server tools, and quotes are checked against the fetched page text. Claude is also available
on Google Cloud Vertex AI (not implemented: it would need OAuth tokens, ideally via a small proxy).

Identify is tuned for latency the same way as the Grok setup (`ClaudeClient+Identify`, `ClaudeClient+Stream`):

- Slim schema (`ReportComponentsTool.slimDefinition`, one fallback carbon estimate per item) and the matching
  `carbonEstimateOnly` prompt: output tokens drive latency.
- `stream: true` with `eager_input_streaming: true` on `report_components`, so `input_json_delta` fragments
  arrive as they are generated; `ProgressThrottle` turns the partial JSON into item names. The prompt asks for
  `scene_title` first and `name` first in each component, since the schema's keys are sorted alphabetically.
- Sonnet 5.5: `thinking: {type: "between_tools"}` (no extended thinking; `disabled` is a 400 on this model) at
  effort `low`. Opus 5.5 always thinks, so it only gets effort `low` and is noticeably slower.
- Anything other than a clean streamed call (HTTP error, text answer, cut-off or invalid JSON) falls back to the
  non-streaming `runTool` loop with retries and nudges. Refusals and timeouts are thrown.
- An Anthropic key that is not scoped to a workspace gets a 400 unless `anthropic-workspace-id` is sent
  (`ANTHROPIC_WORKSPACE_ID`).

Measured on the desk photo (Sonnet 5.5, Oct 2026):

| Call | Time | Notes |
|---|---|---|
| identify, streamed | first item 1.4–2.3 s, done 10–13 s | 6–7 items, no invented model numbers, boxes tighter than Grok's |
| swaps (2 items, effort `low`) | ~10 s | Grok `grok-4.3` took 15–30 s |
| research, brand + model (effort `medium`) | 11–13 s, one outlier at 36 s | cited power, standby and PCF carbon; `low` was no faster |
| research, brand only | ~4 s | returns nothing, as intended |

## 7. Grid data and the smart plug

- Default grid source: **EIA Hourly Electric Grid Monitor** backend,
  `https://www.eia.gov/electricity/930-api/region_data_by_fuel_type/series_data?type[0]=NG&respondent[0]=ISNE&start=MMddyyyy HH:mm:ss&end=…&frequency=hourly&timezone=UTC&limit=10000&offset=0`.
  No key. Response: `[{data: [{FUEL_TYPE_ID, VALUES: {DATES: ["MM/dd/yyyy HH:mm:ss"…], DATA: [MWh…]}}]}]`,
  UTC. It is undocumented, so fixtures pin its shape.
- The documented EIA Open Data API (`api.eia.gov/v2/electricity/rto/fuel-type-data`) was tried first and
  abandoned: 60–100 s per query or 504 errors, even for tiny queries, during testing.
- The grid monitor endpoint takes ~25–30 s for a new query and ~1 s for a repeat within a minute (short
  server cache). The app warms the request at launch (`GridOutlook.warm`), shares in-flight requests
  (`EIAResponseMemo`), archives readings (`GridHistoryArchive`, 7 days, UserDefaults) and waits for live data
  only when there are no readings from the last 12 hours.
- Intensity = generation-weighted IPCC AR5 lifecycle factors (g/kWh): coal 820, gas 490, oil 650,
  nuclear 12, hydro 24, wind 11, solar 45, geothermal 38, biomass 230, other 700; storage excluded. Hours
  with under three fuels, or under half the window's median generation, are dropped as reporting gaps (an
  hour with gas and nuclear reported as 0 read as 625 g/kWh before this filter).
- Zones are Electricity Maps style (`US-NE-ISNE`); the EIA respondent is the last segment (`ISNE`), `US`
  maps to `US48`; Hawaii, Alaska and non-US zones have no EIA data and fall back to the bundled 24-hour shapes.
- Electricity Maps (optional key): free tier is non-commercial with only the last 24 h of history.
- Shelly: Gen2+ local RPC (`Shelly.GetDeviceInfo`, `Switch.GetStatus`, `Switch.Set`, `Schedule.*`) with
  digest auth. Schedules are written to the plug so it follows them with the app closed. Pairing has been
  tried with a Shelly Plug Gen4 on an iPhone Personal Hotspot (enter the plug's `172.20.10.x` IP by hand).

## 8. Units and how metrics are framed

- GreenCore always computes in metric. `DisplayUnits` converts only for display; imperial is the default
  (lb, gal, ft², oz, mi, °F; grid intensity in lb/MWh), Settings → Units switches to metric. Screens that
  show numbers read the `@AppStorage(DisplayUnits.defaultsKey)` value in `body` so they refresh on change.
- Carbon is shown per year (purchase amortized over lifespan plus use) with the lifetime total beside it.
  Electricity is per year. Water, land, plastic and water pollution are shown as what it took to make what
  is pictured; only consumables (food, cups, packaging) also get a per-year figure. Swap savings are split
  into "per year" and "once" (`SwapMath.recursYearly`, `SavingSplit`). Land is shown as plain area (m²/ft²).
- One visibility rule (`Component.displayable`): a metric is shown only if it applies, has a value and is not
  effectively zero (0% recyclable and 0/10 repairability still show). Missing metrics are left off, never
  shown as "not resolved". Swaps also hide metrics whose change rounds to 0%.
- Swaps are ranked by `GreenScore`: the equal-weight mean of per-metric log improvements (clamped to ±ln 4,
  compared per year of the same job). A swap is rejected if any metric gets more than 40% worse or the score
  is under ~2%, so no swap trades one metric for another.
- The metric picker only offers metrics that apply to at least one item in the scan, and the list drops
  items without the selected metric.
- Coffee's factor is per kg of beans; a brewed drink counts only ~6% of its mass as grounds
  (`FoodServing.dryIngredientShare`). Without this a cup read ~10 kg CO2e.
- Barcoded food is per pack when Open Food Facts gives the net quantity (`ScanPipeline+PackBasis` sets
  `Quantities.packNetKg`; `FoodServing.basis` is `.pack(kg)` or `.serving(kg)`), otherwise per serving.
  Per-pack carbon, water and land are per kg × net mass, and the AI's per-serving carbon, water and land
  fallbacks are multiplied by servings in the pack. Plastic is never scaled: the identify prompt defines it
  as all the plastic in the pictured package. A year is `UsageProfile.packsPerWeek` × 52; without a stated
  rate it is the default servings a week converted to packs (`FoodServing.packsPerWeek(of:)`), so yearly
  totals count the same food as before. The pack basis comes from the barcode's records, else the GTIN's
  cache entry, else one lookup per GTIN whose answer T1 reuses (`EvidenceLadder.reusing`); an item whose
  lookup failed is not cached. Cache entries record `packNetKg` and the serving, so a basis change is a miss.
  Food swaps are given the original's pack size and packs a week (a swap without a serving uses the
  original's, and its packaging is scaled by pack sizes), so both sides are the same amount of food. Rows,
  the detail header, the breakdown, the summary and the usage editor say "per pack (…)" or "per serving (…)".

## 9. Usage, questions and phones

- Each usage question gets a "Custom" chip with a full-range slider (`UsageField.customRange`: 0–24 h/day,
  0–21 servings or charges a week, 0–14 packs a week in steps of 0.05, 0–365 wears a year, 0–50 uses a week).
- Item detail has a "Your usage" card (`UsageEditorCard`) built from
  `ImpactEngine.editableUsage(for:)`, which falls back to the engine's defaults when nothing was stored.
- The default typical use for smartphones in `device_defaults.json` is 3 h/day. For battery devices
  (`batteryKWh` set), changing hours also sets charges per week at one charge per 6 h of use
  (`ImpactEngine.usageEdits`); phones currently have no `batteryKWh`, so their electricity is power × hours.

## 10. Onboarding and the leaderboard

- Onboarding asks: location (ZIP first; below it a MapKit map, 110–170 pt tall to fit the screen, flies to
  the state, then the ZIP), household size, meat meals and dairy meals a week (0–21 each), getting around (car, electric car, transit, e-bike with a weekly distance
  each; none is a valid answer), home type, floor area and heating sources (multi-select), and new clothes a
  year. Each step has drawn, animated art (plates that fill, a street scene, a house drawn to scale, a rail of
  shirts) in `OnboardingArt` and `LifestyleStepViews`.
- `UserProfile.commuteKmPerWeekByMode` stores a distance per mode. Walk, bike and work from home are gone;
  old profiles drop those entries. `commuteMode` is optional (nil with no regular travel).
- Food modifier (`reference.meals`): the plant-based share of food's footprint plus the rest scaled by meat
  meals against 9 a week and dairy meals against 10, weighted 1.8 vs 0.45 kg CO2e a meal (Scarborough 2014).
  Plant shares are carbon 0.51, land 0.24, water 0.81 (Poore & Nemecek 2018: an all-plant diet cuts food's
  emissions 49%, land 76%, freshwater 19%). `diet` is derived from the two counts for prompt context.
- Home: `floorAreaM2` (nil = typical for the home type) scales heating and cooling, 52% of home energy (EIA),
  against RECS 2020 averages (detached 2,264 ft², townhouse 1,615, apartment 926; dorm 250 is assumed).
  `heatingSources` is a set; several sources average their modifiers evenly, and an empty set is no heating.
  Yearly electricity uses `heatingModifiers`; home-energy carbon uses `heatingCarbonModifiers` (none 0.66,
  heat pump 0.86, gas 0.98, district 0.98, oil 1.09, electric resistance 1.15). Those are derived, not quoted:
  US home energy 5.95 t CO2e with space heating 34% (EIA RECS 2020 CE4.1, HC6.1), the same heat from each
  source at 80% furnace efficiency (oil 83%) or a seasonal COP of 2.5, eGRID2023's 349.7 g/kWh, and ENERGY STAR
  Portfolio Manager fuel factors. Upstream methane is not counted.
- Clothing modifier: 0.15 + 0.85 × new items a year ÷ 64 (AAFA's US average); the 0.15 base covers shoes and
  second-hand buys.
- Old saved profiles decode: `diet`, `heating` and `clothingHabit` map to counts and sets with the same footprint.
- `LifestyleEstimate` gives the live estimate in onboarding: food, home energy and clothing are per-capita
  carbon × category share × the cohort model's profile modifiers; travel is distance × per-mode factors
  (kg CO2e/km: car 0.25, EV 0.08, transit 0.10, e-bike 0.005); everything else is the remaining share minus an
  average-travel share of 20%. Flights are not asked about.
- Leaderboard tab (code still lives in `Features/Compare`): you plus nine friends (Saahil Shah, Yuti
  Purohit, Nishant Vikramaditya, Vishnu Mangipudi, Sebastian Bagley, Daniel Hoang, Albert Wu, Shuji Hokosawa,
  Louis Liu). Names are dealt in a seeded shuffle; friends are stratified draws from the region's whole-footprint
  distribution (`CohortModel.simulatedFriends`, `regionalDistribution`), and you are your onboarding estimate
  with each category raised to what you scanned in it if larger (`CohortModel.estimate(for:scanned:)`), so both
  sides are whole yearly footprints. Carbon, home electricity, water and land are ranked
  (`leaderboardMetrics`). Water, land and electricity count only the consumption categories' shares of the
  per-capita figure (national withdrawals, farmland and demand also cover industry); land's baseline is one
  world average, so its peers are labelled "worldwide". Each metric's board is built once in the background,
  so switching chips is a lookup. There is no percentile-over-time card and no "simulated" wording in the UI.
- The board opens on **Overall**: everyone ranked by a personal GreenScore (`CohortModel.greenScore`,
  `overallLeaderboard`), the swap rule applied to a whole footprint with the region's typical person (each
  metric's median) as the original. Carbon, electricity, water and land count equally, each log ratio clamped
  to ±ln 4, summed in metric order so ties and rounding don't depend on dictionary order. It shows as 0–100
  points (50 = typical, 100 = 4× smaller on every metric).
- Smart plugs count: a schedule keeps the day's average intensity it shifts away from
  (`PlugSchedule.baselineIntensity`), so `PairedPlug.yearlySavingsKg` is known without a grid fetch. The
  Leaderboard sums it over paired plugs into `ScannedFootprint.scheduledSavingsKg`, which comes off carbon
  only (the electricity is the same), on the carbon board and the overall score alike. Plans saved before the
  baseline existed count after the next re-plan (app foreground or background refresh). Swap ranking still
  leaves plug scheduling unscored (same device, listed last).
- Everyday comparisons ("That's like driving 340 miles in an average gas car!") come from
  `Equivalences.factors`, each cited (EPA equivalencies calculator, EIA, WaterSense/USGS, Water Research
  Foundation, IBWA, sports rulebooks). `pick` offers only counts that read well and is seeded by what's on
  screen plus the day, so the comparison and its opening vary between items, metrics and days but hold still
  while shown. `EquivalenceCallout` puts one on the results summary (single metric), the leaderboard metric
  card, projected swap savings (metric also rotates) and the plug savings card.
- History: delete a scan by swiping, long-pressing, or the "…" menu on the opened scan (with confirmation).
  `AppModel` remembers deleted ids for the session so an open result screen can't save the scan back or start
  a swaps fetch. Cached product metrics are kept; they are keyed by product, not by scan. Feedback notes on a
  deleted scan stay until removed in Settings.

## 11. Results screen design

Photo first with numbered glass pins (the same numbers as the list); selecting an item shows corner
brackets and a name label. Then the metric picker (icons, selected one labeled), the summary card (one big
yearly number, likely range, lifetime / items, a plain-language data-quality line instead of tier codes),
questions banner, the grouped item list and "See greener swaps". Content has bottom margin so the floating
tab bar never covers it. The detail sheet shows the flow (Sankey), usage card, plug card and inspector.

## 12. Testing

- Core logic: `cd Packages/GreenCore && swift test` (~200 tests, under 1 s, Mac host).
- App, default scheme `LiveGreen`: only the critical UI test (`LiveGreenSmokeTests/testDemoScanShowsResults`),
  about 12 s plus build.
- Full UI tours: scheme `LiveGreenFullUITests` (about 3 minutes; includes the 90 s full demo tour).
- Command line:
  ```bash
  xcodebuild -project LiveGreen.xcodeproj -scheme LiveGreen -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -derivedDataPath .build/DerivedData test
  ```
- Live API checks were done with temporary Swift tests gated on environment variables (for example
  `LIVE_XAI`), deleted afterwards. Never commit keys or live tests that need them.
- Simulator driving tips: launch arguments `-DemoMode YES`, `-SkipOnboarding YES`, `-InMemoryStore YES`,
  `-ScanMode photo|ar|barcode`, `-AIProvider grok|claude`. `xcrun simctl addmedia` puts a
  test photo in the library; `xcrun simctl ui <device> appearance dark` switches appearance. Taps right after
  `launch` often land before the app is ready; wait a couple of seconds.

## 13. Known gaps and ideas

- Camera, Integrated view (ARKit) and barcode scanning have only run in the simulator; test on a device.
- Real Shelly pairing and schedule writes are untested on hardware.
- Grok boxes are loose; a bundled detector or pointing via on-device segmentation could tighten them.
- Several reference values are marked `verified: false` (fiber factors, device defaults, many material
  end-of-life rows, grid hourly shapes, cohort sigmas and modifiers, home/heating modifiers, travel factors).
- Onboarding's "everything else" is about half the estimate; flights are not covered.
- The leaderboard's friends are generated from the cohort model, not real accounts.
- Research is on the scan's critical path for branded items; a slow web search (one 36 s run seen) delays the
  result. It could move behind a preliminary result.
